# 弹幕提取

## 当前边界

弹幕提取环节会把直播弹幕解析成 JSONL 记录。顶层字段用于记录弹幕事件、解析结果和调试信息；`query_payload` 用于给下游“小程序 API 提取岗位信息”环节消费。

目前下游主要消费 `query_payload`。因此，顶层字段即使成功解析出来，如果没有映射进 `query_payload`，也不会影响实际岗位搜索。

当前已进入 `query_payload` 的有效映射：

- `keyword` -> `intention_job`
- `city` -> `intention_location`
- `education` -> `education`
- `graduate_time` -> `graduate_time`，`25`-`28` 届归一为 `2025`-`2028`，更早归一为 `往届`

## 其他字段加入顶层字段的可能性

后续可以优先考虑解析这些与 payload 字段对应的顶层字段：

- `major`：专业。专业名称非常开放，建议只在“专业/学/我是 XX 的”等明确上下文中高置信提取；优先支持“专业不限”。
- `job_type`：工作性质，如 `全职`、`实习`、`兼职`。需要避免把“实习”同时误判为岗位关键词。
- `is_unlimited_major`：是否不限专业，可由“专业不限 / 不限专业 / 不看专业”解析。
- `intention_company`：意向公司，只有在“想去 XX / XX 公司”语义明确时再解析。
- `company_type`：就业方向或公司类型。需要先确认后端枚举，不能简单把顶层 `industry` 直接映射过去。
- `jobCategory`：岗位类别。需要确认后端分类体系，与 `keyword`、`industry` 的关系不能混用。
- `timeType`：时间类型，如“今日最新”“即将到期”。需要确认直播间表达和后端支持值。
- `order_by`：排序方式，更适合作为系统策略或下游配置，不一定适合从弹幕中解析。
- `query_str`：关键词搜索。当前不建议和 `intention_job` 同时传，避免后端双重过滤导致结果过窄。

已解析但目前没有明确 payload 去向的字段：

- `salary`：薪资要求。下游搜索接口当前没有确认可用字段，暂不传。
- `experience`：工作年限。下游搜索接口当前没有确认可用字段，暂不传。
- `industry`：行业。可能和 `company_type` 或 `jobCategory` 有关系，但需要确认后端语义和枚举后再映射。

## LLM 辅助解析方向

未来可以让 LLM 参与长尾字段解析，但建议作为兜底，不直接全信。

适合 LLM 辅助的场景：

- 长尾专业名，如“城市地下空间工程”“智能制造工程”。
- 口语化毕业年份表达，如“明年毕业”“今年应届”“27 秋招”。
- 复杂组合条件，如“计算机 26 届想找上海产品实习”。

建议的控制策略：

- 规则层先处理高频、明确、低风险表达。
- LLM 输出后做字段级校验，例如长度、黑名单、枚举值、上下文触发词。
- 低置信字段只写顶层调试字段，不进入 `query_payload`。
- 只有确认字段语义和后端枚举后，再接入 payload。

## 优先级建议

短期优先：

- 保持 `query_payload` 兼容，不删除、不改名、不改变已消费字段类型。
- 扩展顶层解析时，优先选择能未来映射到 payload 的字段。
- 对暂未消费的字段，在文档中明确“仅顶层记录，不参与搜索”。

中期优先：

- 建立顶层字段到 payload 字段的显式映射表。
- 为 `major`、`job_type`、`graduate_time` 增加更完整的测试样例。
- 确认后端枚举后，再考虑 `company_type`、`jobCategory`、`timeType` 的映射。
