# 直播弹幕解析系统 — 筛选流程与规则说明

## 1. 系统概述

本模块用于直播间自动化查岗场景。当用户在直播间发送弹幕时，系统需要从大量弹幕中识别出"查询岗位"意图，提取结构化信息，并驱动小程序完成搜索展示。

直播间会提示用户查询样例格式：**查北京产品经理岗位**

系统支持提取以下字段，其中**岗位关键词为必填**，其余均为可选：

| 字段 | 必填 | 说明 | 示例 |
|------|------|------|------|
| 岗位关键词 | ✅ 是 | 用户想查询的职位 | 产品经理、Java、前端 |
| 城市 | 否 | 工作地点 | 北京、深圳、杭州 |
| 薪资 | 否 | 薪资范围或要求 | 15k-25k、1万-2万、面议 |
| 工作年限 | 否 | 经验要求 | 3年、1-3年、应届 |
| 学历 | 否 | 学历门槛 | 本科、硕士、985/211 |
| 行业 | 否 | 目标行业 | 互联网、金融、游戏 |

## 2. 整体架构

系统采用**三层漏斗**架构，逐层过滤，兼顾效率与准确率：

```
弹幕输入
  │
  ▼
┌──────────────┐
│ 第一层：噪声过滤 │ ← 过滤无意义弹幕（约 70-80%）
└──────┬───────┘
       │ 疑似有效弹幕
       ▼
┌──────────────────────┐
│ 第二层：规则解析（多字段） │ ← 关键词 + 正则，命中则直接输出
└──────┬───────────────┘
       │ 未命中
       ▼
┌──────────────┐
│ 第三层：LLM 兜底 │ ← 大模型处理口语化、模糊表达
└──────┬───────┘
       │ 有效查询
       ▼
┌──────────────────────┐
│ 去重 & 队列（全字段比对） │ ← 合并重复查询，排队执行
└──────────────────────┘
```

设计思路：规则层零延迟、零成本，能覆盖绝大多数符合提示格式的标准弹幕；LLM 层只处理规则漏掉的口语化长尾表达，控制调用量和整体延迟。

## 3. 第一层：噪声过滤

### 3.1 目标

快速丢弃明显与查岗无关的弹幕，减少后续层的处理压力。

### 3.2 过滤规则

#### 3.2.1 长度限制

| 条件 | 阈值 | 说明 |
|------|------|------|
| 最短长度 | 2 字符 | 单字弹幕信息量不足 |
| 最长长度 | 100 字符 | 超长文本通常为刷屏或灌水 |

#### 3.2.2 噪声关键词（精确匹配）

以下弹幕会被直接丢弃：

> 哈哈、666、牛、厉害、加油、谢谢、主播、来了、dd、打卡、签到、1、关注、点赞、转发、好看、收到

此列表可根据实际直播间弹幕特征持续扩充。

#### 3.2.3 噪声正则匹配

| 模式 | 说明 | 示例 |
|------|------|------|
| `^[哈嘿嗯啊噢哦嘻呵]{2,}$` | 纯语气词重复 | 哈哈哈、嘿嘿嘿 |
| `^[0-9]{1,6}$` | 纯数字刷屏 | 666、888、1 |
| `^[!！?？.。,，~～]+$` | 纯标点符号 | ！！！、？？？ |
| `^[emoji]+$` | 纯 emoji 表情 | 😂🔥👍 |

### 3.3 过滤效果

在典型直播间中，噪声过滤层可过滤约 **70-80%** 的弹幕，仅放行疑似有意义的内容进入下一层。

## 4. 第二层：规则解析

### 4.1 目标

通过关键词匹配和正则规则，对符合常见查询模式的弹幕进行快速、多字段的结构化解析，零延迟返回结果。

### 4.2 意图识别

系统维护一组**触发词**，弹幕中出现以下任一词汇即判定为查岗意图：

> 查、找、搜、看看、有没有、有无、帮我、我想、想找、求、招不招、还招、岗位、职位、工作、招聘

### 4.3 实体提取

规则层对每条弹幕进行**全局多字段扫描**，各字段独立提取，互不依赖。

#### 4.3.1 岗位关键词提取（必填）

系统维护高频岗位词库，按词长降序匹配（优先匹配长词，避免"数据分析"被拆为"数据"）。当前收录岗位关键词包括：

**技术类：** 前端、后端、Java、Python、C++、Go、算法、数据分析、测试、运维、安卓、Android、iOS、嵌入式、大数据、机器学习、深度学习、NLP、全栈、架构师

**产品与设计类：** 产品经理、UI、UX、设计、视觉设计、平面设计

**运营与商务类：** 运营、市场、销售、新媒体、内容运营、商务、电商、直播运营、文案

**职能类：** HR、人事、财务、法务、行政、客服、采购、供应链

**管理类：** 项目经理、技术总监、CTO

**其他：** 实习

#### 4.3.2 城市提取

系统维护城市词库，从弹幕文本中匹配城市名称。当前收录 35 个主要城市：

> 北京、上海、广州、深圳、杭州、成都、重庆、武汉、南京、苏州、西安、长沙、郑州、东莞、天津、青岛、宁波、厦门、大连、珠海、佛山、合肥、福州、济南、昆明、贵阳、海口、无锡、常州、温州、石家庄、哈尔滨、沈阳、太原 等

#### 4.3.3 薪资提取

通过正则表达式匹配，按优先级依次尝试以下 6 种模式：

| 模式 | 说明 | 输入示例 | 标准化输出 |
|------|------|----------|-----------|
| `数字k-数字k` | k/K 区间 | 15k-25k、20K-30K | 15k-25k |
| `数字万-数字万` | 万/w/W 区间 | 1万-2万、1w-2w | 1万-2万 |
| `数字-数字`（≥4位） | 纯数字区间 | 8000-12000 | 8000-12000 |
| `数字k` | 单个 k 值 | 15k、20K | 15k |
| `数字万` | 单个万值 | 2万、2w | 2万 |
| `面议` | 薪资面议 | 面议、薪资面议 | 面议 |

说明：纯数字区间要求至少 4 位数字，避免 "1-3年" 这类经验表达被误识别为薪资。

#### 4.3.4 工作年限提取

通过正则表达式匹配，按优先级依次尝试以下 6 种模式：

| 模式 | 说明 | 输入示例 | 标准化输出 |
|------|------|----------|-----------|
| `数字-数字年` | 年限区间 | 1-3年、1~3年 | 1-3年 |
| `数字年以上` | 最低年限 | 3年以上 | 3年以上 |
| `数字年+` | 最低年限变体 | 5年+ | 5年以上 |
| `数字年(经验)` | 固定年限 | 3年、3年经验 | 3年 |
| `应届` | 应届毕业生 | 应届、应届生 | 应届 |
| `无经验` | 不限经验 | 无经验、经验不限 | 不限 |

#### 4.3.5 学历提取

通过关键词匹配 + 归一化映射，将各种表达统一为标准学历值：

| 输入关键词 | 标准化输出 |

| 博士 | 博士 |
| 硕士、研究生 | 硕士 |
| 本科、大本 | 本科 |

#### 4.3.6 行业提取

系统维护行业词库，当前收录 40+ 个行业关键词，按词长降序匹配：

> 互联网、金融、教育、医疗、电商、游戏、社交、物流、房地产、汽车、新能源、制造业、零售、传媒、广告、文娱、旅游、餐饮、农业、人工智能、AI、区块链、芯片、半导体、通信、生物科技、医药、保险、证券、银行、咨询、法律、会计、外贸、跨境、SaaS、云计算、网络安全、物联网、智能硬件

### 4.4 匹配逻辑

规则层对每条弹幕**先全局预提取所有可选字段**（城市、薪资、经验、学历、行业），再按以下优先级判断岗位关键词：

**路径 A — 触发词 + 岗位关键词**

1. 检测弹幕是否包含触发词
2. 去除触发词和修饰词（"的"、"岗位"、"职位"等）
3. 从剩余文本提取岗位关键词（排除已识别的城市避免干扰）
4. 若提取到岗位关键词，连同所有已提取的可选字段一起输出

**路径 B — 无触发词，纯实体组合**

当弹幕没有触发词时，系统仍然尝试提取岗位关键词。判定条件：去除所有已识别实体（城市、薪资、经验、学历、行业、岗位）和修饰词后，剩余文本不超过 10 个字符。这保证了像 "杭州Java 1-3年 985" 这样没有触发词但意图明确的弹幕也能被命中。

### 4.6 规则层的边界

以下类型的弹幕规则层**无法覆盖**，会被放行至 LLM 层：

- 口语化表达，无标准触发词或岗位词（如"有啥坑给推荐推荐"）
- 模糊意图（如"刚毕业能干啥"）
- 查询对象不是岗位（如"杭州有没有啥好的互联网公司"）
- 非常规岗位名称，不在词库中

## 5. 第三层：LLM 兜底解析

### 5.1 目标

处理规则层无法覆盖的口语化、模糊表达，通过大模型的语义理解能力进行意图判断和实体提取。

### 5.2 调用策略

- 仅对通过噪声过滤且规则未命中的弹幕调用 LLM
- 推荐使用轻量模型（如 gpt-4o-mini、deepseek-chat 等）控制延迟
- 设置超时阈值 3 秒，超时则放弃该条弹幕
- temperature 设为 0，确保输出稳定

### 5.3 Prompt 设计要点

系统 Prompt 对模型的约束包括：

1. 明确任务：判断弹幕是否包含查岗意图
2. 定义输出格式：仅输出 JSON
3. 定义字段：intent（search / none）、keyword（必填）、city / industry / salary / experience / education（选填）
4. 提供 few-shot 示例覆盖多种表达风格
5. 明确兜底规则：无法判断时返回 `{"intent": "none"}`

### 5.4 LLM 能覆盖的长尾场景示例

| 弹幕 | 期望输出 |
|------|----------|
| 有啥坑给推荐推荐 | intent=search（泛查询） |
| 杭州有没有啥好的互联网公司 | intent=none（查公司非查岗） |
| 刚毕业能干啥 | intent=search, keyword=实习 |
| 深圳有没有前端的活 3年经验 | keyword=前端, city=深圳, experience=3年 |

## 6. 去重机制

### 6.1 问题场景

多个用户可能在短时间内发送相同或相似的查询（如多人同时发"查北京产品经理"），若不做去重，小程序会重复执行同一搜索。

### 6.2 去重策略

采用滑动窗口去重，核心逻辑：

- 以**全部已提取字段**（岗位 + 城市 + 薪资 + 经验 + 学历 + 毕业年份 + 行业）拼接生成哈希作为去重键
- 设定去重窗口（默认 60 秒）
- 窗口内相同查询仅放行第一条，后续丢弃
- 过期条目自动清理

全字段去重保证了同一岗位在不同条件下不会被误去重。例如 "查北京产品经理" 和 "查北京产品经理 15k-25k" 视为不同查询，会分别执行。

## 7. 输出数据结构

每条成功解析的弹幕输出以下结构化数据，传递给下游的小程序控制模块：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| keyword | string | 是 | 岗位关键词，如"产品经理" |
| city | string | 否 | 城市，如"北京" |
| salary | string | 否 | 薪资要求，如"15k-25k" |
| experience | string | 否 | 经验要求，如"3年" |
| education | string | 否 | 学历要求，如"本科" |
| industry | string | 否 | 行业，如"互联网" |
| raw_text | string | 是 | 原始弹幕文本 |
| source | string | 是 | 解析来源："rule" 或 "llm" |

## 9. 扩展与优化方向

**词库扩充：** 根据小程序实际支持的岗位数据和用户行为持续补充岗位关键词、城市列表和行业词库，提高规则层覆盖率。

**批量调用：** 弹幕高峰期可攒 2-3 秒窗口的弹幕批量送入 LLM，减少请求次数。

**优先级队列：** 按弹幕出现频次或时间排序，高频查询优先执行，保证直播间互动感。

**反馈闭环：** 记录 LLM 命中的弹幕模式，定期将高频模式沉淀为规则，逐步降低 LLM 依赖。
