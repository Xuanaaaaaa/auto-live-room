# 空查询误触发音频播报问题分析与修复

本文用于指导 Windows/WSL 环境中的 agent 修复一个直播链路问题：

```text
没有新弹幕时，系统偶尔自动生成并播放一条岗位语音；
播报内容是“没有筛选条件时返回的第一个岗位”。
```

结论先行：这个问题优先不像 OBS 音频播放脚本的问题，而是 **小程序 UI 自动化控制脚本写回状态事件到弹幕 JSONL 后，被主链路编排器误当成新弹幕查询处理**。

## 1. 当前相关模块

### 1.1 主链路：自动化直播间

主链路大致是：

```text
弹幕 JSONL
  -> 链路监控/orchestrator.py
  -> 小程序 API 搜索
  -> LLM 生成解说
  -> TTS 生成 mp3
  -> 链路监控/events/events_*.jsonl 写 audio_path
  -> OBS 音频旁路播放
```

关键文件：

```text
链路监控/orchestrator.py
小程序API提取岗位信息/aibz_job_search.py
Obs_auto/obs_audio_player.py
scripts/run_obs_audio.sh
```

### 1.2 小程序 UI 自动化控制模块

当前自动化脚本目录：

```text
automation-main/
```

重点文件：

```text
automation-main/watch-danmu.js
automation-main/lib/automation-core.js
```

`watch-danmu.js` 的职责是监听弹幕解析输出 JSONL，把新弹幕查询转换为小程序 UI 筛选条件，然后串行驱动小程序搜索。

## 2. 问题现象

实际观察：

1. 没有新弹幕发上来。
2. 系统仍然生成了新的 TTS mp3。
3. OBS 自动播放了这条新音频。
4. 音频内容对应“无筛选条件下默认返回的第一个岗位”。

这个现象说明：

```text
OBS 音频脚本只是播放了一个已经生成的 audio_path；
真正异常的是上游又产生了一条新的 completed trace。
```

## 3. 根因分析

### 3.1 OBS 音频脚本不是生成源

`Obs_auto/obs_audio_player.py` 只监听 `events_*.jsonl` 中的音频事件。

其逻辑是：

```text
读取 events JSONL
  -> 找 stage=completed 或 stage=synthesized
  -> 找 audio_path
  -> 调 OBS WebSocket 播放这个 mp3
```

它不会做这些事情：

```text
不会读取弹幕
不会调用小程序 API
不会调用 LLM
不会调用 TTS
不会生成 mp3
```

所以如果出现“新 mp3 被生成”，原因应在 OBS 音频脚本上游。

### 3.2 watch-danmu.js 会写状态事件回同一个弹幕 JSONL

在 `automation-main/watch-danmu.js` 中，自动化脚本会把状态事件追加写回当前 JSONL 文件：

```js
function writeStatusEvent(filePath, event) {
  fs.appendFileSync(filePath, JSON.stringify(event, null, 0) + '\n')
}
```

写入的事件包括：

```js
{
  type: 'automation_started',
  trace_id,
  ts,
  criteria,
}
```

```js
{
  type: 'automation_done',
  trace_id,
  ts,
  status: 'ok',
}
```

```js
{
  type: 'automation_failed',
  trace_id,
  ts,
  status: 'failed',
  error: err.message,
}
```

这些状态事件本来是给自动化模块自己记录进度的，不是弹幕查询。

### 3.3 watch-danmu.js 自己会跳过 automation_*，但 orchestrator 不会

`watch-danmu.js` 里有过滤逻辑：

```js
function isQueryEvent(record) {
  if (record.type && record.type.startsWith('automation_')) return false
  return !!(record.keyword || (record.query_payload && record.query_payload.intention_job))
}
```

所以 UI 自动化脚本自己不会重复消费 `automation_*`。

但是主链路 `链路监控/orchestrator.py` 目前会 tail 同一个弹幕 JSONL，并且对每一行合法 JSON 都调用：

```python
trace = orch.handle(record)
```

它没有先判断：

```text
这行是不是弹幕查询？
这行是不是 automation_* 状态事件？
这行有没有有效 query_payload？
这行有没有 keyword？
```

于是 `automation_started` / `automation_done` / `automation_failed` 也可能被当成弹幕记录处理。

### 3.4 状态事件缺少 query_payload，导致空搜索

`orchestrator.py` 搜索阶段逻辑类似：

```python
payload = trace["danmu"].get("query_payload") or {}
res = search_jobs_from_payload(payload, ...)
```

当输入记录是：

```json
{"type":"automation_done","trace_id":"...","status":"ok"}
```

经过 `_slim_danmu()` 后，关键字段大概率都是：

```json
{
  "keyword": null,
  "raw_text": null,
  "query_payload": null
}
```

然后：

```python
payload = {}
```
最终调用小程序 API 时变成空 filters。

`aibz_job_search.py` 会清理空值，空 filters 仍然可能发给后端：

```python
body = _clean_params(filters)
```

空搜索通常会返回默认岗位列表第一页，因此下游会拿第一个岗位生成解说和 TTS。

最终表现就是：

```text
没有新弹幕
  -> 自动化状态事件被误消费
  -> 空搜索
  -> 默认第一个岗位
  -> TTS
  -> OBS 播放
```

## 4. 推荐修复方案

建议分两层修复：一层从源头避免污染弹幕 JSONL；一层在主链路加防御过滤。

## 方案 A：自动化状态事件不要写回弹幕 JSONL

这是首选修复。

### 4.1 改造目标

`watch-danmu.js` 不应把状态事件写回：

```text
弹幕提取/DouyinLiveWebFetcher/output/{live_id}_{timestamp}.jsonl
```

而应该写到独立状态文件，例如：

```text
automation-main/test-runs/watch-{RUN_ID}/status.jsonl
```

或者支持环境变量：

```bash
AUTOMATION_STATUS_JSONL=/path/to/automation-status.jsonl
```

推荐兼容方式：

```text
如果设置 AUTOMATION_STATUS_JSONL：写到该文件
否则默认写到 RUN_DIR/status.jsonl
永远不要默认写回弹幕 JSONL
```

### 4.2 需要调整的代码点

文件：

```text
automation-main/watch-danmu.js
```

当前逻辑大概是：

```js
const jsonlPath = findLatestJsonl(DANMU_JSONL_DIR)

if (jsonlPath) {
  writeStatusEvent(jsonlPath, {
    type: 'automation_started',
    ...
  })
}
```

建议改成：

```js
const STATUS_JSONL = process.env.AUTOMATION_STATUS_JSONL || path.join(RUN_DIR, 'status.jsonl')
```

然后统一：

```js
writeStatusEvent(STATUS_JSONL, {
  type: 'automation_started',
  ...
})
```

`automation_done` 和 `automation_failed` 同理。

### 4.3 注意

保留 `isQueryEvent()` 跳过 `automation_*` 的逻辑没有坏处，但仅靠它不够，因为主链路也在读同一个弹幕 JSONL。

## 方案 B：orchestrator.py 增加查询事件过滤

这是必要的防御性修复。即使未来其他脚本误写状态事件，主链路也不应触发空搜索。

### 4.4 改造目标

主链路只处理真正的弹幕查询记录。

建议新增函数：

```python
def is_query_record(record: Dict[str, Any]) -> bool:
    record_type = record.get("type")
    if isinstance(record_type, str):
        if record_type.startswith("automation_"):
            return False
        if record_type not in ("danmu_query",):
            return False

    payload = record.get("query_payload")
    keyword = record.get("keyword")

    if keyword:
        return True

    if isinstance(payload, dict):
        intention_job = payload.get("intention_job")
        query_str = payload.get("query_str")
        intention_company = payload.get("intention_company")
        intention_location = payload.get("intention_location")
        education = payload.get("education")
        job_type = payload.get("job_type")
        company_type = payload.get("company_type")

        return any([
            bool(intention_job),
            bool(query_str),
            bool(intention_company),
            bool(intention_location),
            bool(education),
            bool(job_type),
            bool(company_type),
        ])

    return False
```

然后在主循环中：

```python
for record in tail_jsonl(danmu_path, from_start=args.from_start):
    if not is_query_record(record):
        print(f"[skip] non-query record: type={record.get('type')!r}")
        continue
    ...
```

### 4.5 更保守的过滤条件

如果业务要求“必须有岗位关键词才搜索”，可以更严格：

```python
if not keyword and not payload.get("intention_job") and not payload.get("query_str"):
    return False
```

这样可以避免只带 `education` 之类弱条件的空泛搜索。

考虑你当前问题是“无筛选第一个岗位”，更推荐严格一点：

```text
至少有 keyword / intention_job / query_str / intention_company 之一
```

城市、学历这类字段单独存在时，不一定应该触发搜索。

## 5. 建议修复优先级

推荐顺序：

```text
1. 先改 watch-danmu.js：状态事件写到独立 status.jsonl
2. 再改 orchestrator.py：跳过非查询记录和空查询
3. 保持 obs_audio_player.py 不动
```

原因：

- `watch-danmu.js` 写回弹幕 JSONL 是污染源。
- `orchestrator.py` 缺少输入过滤是放大器。
- `obs_audio_player.py` 只是播放器，不是生成源。

不再出现 automation_done
不再出现 automation_failed

期望状态事件写到这里。

## 7. 排查命令

问题复现后，先看最新音频：

```bash
ls -lt 链路监控/audio | head
```

看最新 events：

```bash
ls -lt 链路监控/events | head
tail -n 50 链路监控/events/最新events文件.jsonl
```

重点找最新 `received` 事件：

```json
"keyword": null,
"raw_text": null,
"query_payload": null
```

如果出现这种记录后又有 `searched/narrated/synthesized/completed`，说明主链路消费了非查询事件。

再看弹幕 JSONL：

```bash
tail -n 50 弹幕提取/DouyinLiveWebFetcher/output/当前直播间文件.jsonl
```

如果看到：

```json
{"type":"automation_started", ...}
{"type":"automation_done", ...}
{"type":"automation_failed", ...}
```

说明自动化状态污染了弹幕输入流。

## 8. 不建议的修复

不建议只改 OBS 音频脚本来“过滤某些音频”。

原因：

```text
音频脚本看到 audio_path 时，异常搜索、异常文案、异常 TTS 已经发生；
即使不播放，资源也已经消耗了，trace/events 也被污染。
```

正确修复点应在：

```text
输入事件隔离 + 主链路查询过滤
```

## 9. 预期最终状态

修复后：

```text
没有新弹幕
  -> 不会产生新 trace
  -> 不会搜索默认岗位
  -> 不会生成新 TTS
  -> OBS 不会自动播报
```

真实查询弹幕：

```text
弹幕 JSONL 新增有效 query_payload
  -> orchestrator 正常处理
  -> TTS 生成 mp3
  -> events 写 audio_path
  -> OBS 音频脚本播放
```
